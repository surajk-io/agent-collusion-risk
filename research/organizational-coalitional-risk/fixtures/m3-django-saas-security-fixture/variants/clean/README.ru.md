# Django Multi-Tenant SaaS Starter

Готовая к продакшену основа для мультитенантного B2B SaaS на **Django 5 + Django REST Framework**. Из коробки — **построчная мультитенантность** (row-level), **ролевая модель доступа (RBAC)**, **поток приглашений**, **JWT-аутентификация** и протестированная гарантия того, что один тенант никогда не прочитает и не изменит данные другого.

Запускается где угодно на **sqlite** (поэтому набор тестов воспроизводится на любой машине) и переключается на **Postgres** в продакшене одной переменной `DATABASE_URL`.

---

## Зачем это нужно

Большинство «SaaS-болерплейтов» либо вовсе не реализуют мультитенантность, либо прикручивают её как поле `tenant_id`, по которому нужно не забыть отфильтровать, — а именно так и происходят утечки данных между тенантами. Этот стартер делает изоляцию **поведением по умолчанию** на уровне ORM: тенант-ограниченный менеджер «закрыт по умолчанию», а выход за пределы тенанта требует явного, отслеживаемого исключения. Главное инженерное содержание — в модели тенантности и её компромиссах, честно разобранных ниже.

## Возможности

- **Построчная мультитенантность** — граница `Tenant` (организация), базовая тенант-ограниченная модель и менеджер, который автоматически фильтрует каждый запрос по активному тенанту.
- **RBAC** — `Membership` связывает `User` и `Tenant` ролью (`owner` / `admin` / `member`). Классы прав DRF разграничивают действия по роли.
- **Приглашения** — приглашение по почте → ожидающий `Invitation` → принятие → `Membership`. Токенизированные, с истечением срока, отправка только для owner/admin.
- **JWT-аутентификация** — `djangorestframework-simplejwt`. Регистрация атомарно создаёт пользователя, тенант и членство **owner**.
- **Чистые настройки** — `base / dev / test / prod`, управление через переменные окружения (`django-environ`), поддержка `DATABASE_URL`, усиление безопасности в проде.
- **Контейнеризация** — `Dockerfile` и `docker-compose.yml` (web + Postgres + Redis) для запуска, близкого к продакшену.
- **CI** — GitHub Actions с `ruff` и `pytest` на Python 3.10 и 3.12.

## Архитектура

```
config/
  settings/          base.py · dev.py · test.py · prod.py
  urls.py · wsgi.py · asgi.py
apps/
  common/            механика тенантности (ядро)
    tenant_context.py  ContextVar с активным тенантом (безопасен для потоков и async)
    models.py          TimeStampedModel, TenantManager, TenantScopedModel
    permissions.py     HasActiveTenant, IsTenantMember/Admin/Owner
  accounts/          кастомный User (вход по email) и регистрация
  tenants/           Tenant, Membership (RBAC), Invitation, middleware, API
  projects/          Project — образцовый тенант-ограниченный ресурс
tests/               изоляция · RBAC · регистрация · приглашения
```

### Как запрос определяет свой тенант

1. **`TenantMiddleware`** определяет активный тенант в таком порядке: заголовок `X-Tenant` (совпадает с `Tenant.slug`), поддомен запроса (`acme.example.com`) или — для сессионных пользователей — единственное членство пользователя. Затем связывает этот тенант с `ContextVar`.
2. **`TenantManager`** каждой тенант-ограниченной модели читает этот `ContextVar` и фильтрует `get_queryset()` по активному тенанту. Если тенант не привязан, менеджер возвращает **ничего** (закрыт по умолчанию), а не всё подряд.
3. **`TenantScopedModel.save()`** автоматически проставляет активный тенант новым строкам, поэтому прикладной код никогда не задаёт `tenant` вручную и не может ошибиться.
4. **RBAC** обеспечивается классами прав DRF, которые находят `Membership` вызывающего в активном тенанте и проверяют роль.

> **Одна тонкость, о которой стоит сказать прямо (это реальный вопрос на собеседовании):** middleware Django выполняется *до* того, как DRF аутентифицирует запрос, поэтому при JWT в момент работы middleware `request.user` ещё анонимен. Поэтому middleware определяет только *тенант* (заголовок и поддомен не зависят от пользователя), а *членство* вызывающего вычисляется лениво на уровне прав, когда DRF уже аутентифицировал пользователя. См. `apps/tenants/utils.py`.

### Модель тенантности: построчная против схемной — честные компромиссы

Этот стартер использует **построчную (shared-schema) мультитенантность**: строки всех тенантов лежат в одних и тех же таблицах и различаются внешним ключом `tenant_id`. Основные альтернативы — **схема на тенант** (отдельная схема Postgres у каждого, напр. `django-tenants`) и **база на тенант**.

**Почему здесь построчная:**

- **Запускается и тестируется где угодно.** Подходам «схема на тенант» и «база на тенант» нужны Postgres и обвязка переключения схем; построчная работает на sqlite, поэтому весь набор тестов воспроизводится без инфраструктуры — а это и есть смысл *стартера*.
- **Дешёвый и быстрый онбординг.** Создание тенанта — один `INSERT`, а не `CREATE SCHEMA` и миграции. Тысячи мелких тенантов остаются дешёвыми.
- **Кросс-тенантная аналитика тривиальна** — это просто запросы без фильтра по тенанту (через явный «неограниченный» менеджер).
- **Один набор миграций.** Миграции схемы выполняются один раз, а не по разу на тенант.

**Чем приходится платить (и как это смягчено в стартере):**

- **Изоляцию обеспечивает прикладной код, а не база данных.** Забытый `.filter(tenant=...)` — это утечка. *Смягчение:* ограниченный менеджер стоит **по умолчанию** и закрыт по умолчанию; выход за пределы тенанта — явный вызов `all_tenants` / `unscoped()`; изоляция покрыта тестами. Для эшелонированной защиты в Postgres можно дополнительно включить политики **Row-Level Security (RLS)**.
- **Проблема «шумного соседа».** Тяжёлые запросы одного тенанта делят таблицы и индексы со всеми. *Смягчение:* хорошие составные индексы, начинающиеся с `tenant_id`; пул соединений; индивидуальные лимиты запросов.
- **Пооперационная связанность тенантов.** Нельзя так же легко восстановить, выгрузить или перенести один тенант, как при подходе «база на тенант».
- **Слабее «радиус поражения» для комплаенса.** Часть регулируемых корпоративных клиентов по договору требует физического разделения данных.

**Когда переходить дальше:** начинайте с построчной; крупные или чувствительные к комплаенсу тенанты переводите на **схему- или базу-на-тенант** (гибрид: большинство тенантов делят схему, отдельные VIP получают свою). Абстракция `tenant_context` намеренно остаётся единственным местом, которое «знает», как выбирается текущий тенант, поэтому смена стратегии разрешения затронет один модуль, а не весь код.

## Быстрый старт

```bash
# 1. Окружение
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # для дева не обязательно

# 2. База данных (по умолчанию sqlite)
python manage.py migrate
python manage.py createsuperuser   # по желанию, для /admin

# 3. Запуск
python manage.py runserver
```

Запуск тестов:

```bash
pytest
```

Линтер:

```bash
ruff check .
```

## Обзор API

Базовый путь — `/api/v1/`. Все ресурсные эндпоинты требуют JWT (`Authorization: Bearer <token>`) и, кроме отмеченных, активный тенант в заголовке `X-Tenant: <slug>`.

| Метод | Путь | Аутентификация | Заголовок тенанта | Примечания |
| --- | --- | --- | --- | --- |
| `POST` | `/auth/register/` | нет | нет | Создаёт пользователя + тенант + членство **owner**; возвращает JWT |
| `POST` | `/auth/token/` | нет | нет | Получить access/refresh токены (`email` + `password`) |
| `POST` | `/auth/token/refresh/` | нет | нет | Обновить access-токен |
| `GET` | `/tenants/` | JWT | нет | Тенанты, в которых вы состоите (с вашей ролью) |
| `PATCH` | `/tenants/{id}/` | JWT | да | Изменить тенант — только owner/admin |
| `GET` | `/members/` | JWT | да | Участники активного тенанта |
| `PATCH`/`DELETE` | `/members/{id}/` | JWT | да | Управление участниками — только owner/admin; owner защищён |
| `GET` | `/invitations/` | JWT | да | Ожидающие/выданные приглашения |
| `POST` | `/invitations/` | JWT | да | Пригласить по почте — только owner/admin |
| `POST` | `/invitations/accept/` | JWT | нет | Принять приглашение по `token` (токен задаёт тенант) |
| `GET`/`POST` | `/projects/` | JWT | да | Список/создание проектов (любой участник) |
| `GET`/`PATCH` | `/projects/{id}/` | JWT | да | Получить/изменить проект (любой участник) |
| `DELETE` | `/projects/{id}/` | JWT | да | Удалить проект — только owner/admin |

`GET /healthz/` — проверка работоспособности без аутентификации.

### Пример сценария

```bash
# Регистрация — создаёт тенант «Acme» и делает вас его владельцем
curl -s -X POST http://localhost:8000/api/v1/auth/register/ \
  -H 'Content-Type: application/json' \
  -d '{"email":"founder@acme.io","password":"Sup3r-Secret-pw!","tenant_name":"Acme"}'
# -> { "access": "...", "tenant": { "slug": "acme", "role": "owner" }, ... }

ACCESS=...   # вставьте access-токен

# Создать проект в Acme
curl -s -X POST http://localhost:8000/api/v1/projects/ \
  -H "Authorization: Bearer $ACCESS" -H 'X-Tenant: acme' \
  -H 'Content-Type: application/json' -d '{"name":"Редизайн сайта"}'

# Пригласить коллегу (только owner/admin)
curl -s -X POST http://localhost:8000/api/v1/invitations/ \
  -H "Authorization: Bearer $ACCESS" -H 'X-Tenant: acme' \
  -H 'Content-Type: application/json' -d '{"email":"teammate@acme.io","role":"member"}'
```

## Тесты и гарантия изоляции

Набор тестов (`tests/`, pytest + pytest-django) — это доказательство того, что тенантность работает, а не просто заявление:

- **`tests/test_tenant_isolation.py`** — queryset тенанта A никогда не возвращает строки B (и на уровне ORM, и API); A получает `404` (а не `200`) при запросе объекта B по id; A не может изменить объект B; менеджер закрыт по умолчанию, когда тенант не привязан; при сохранении проставляется тенант вызывающего.
- **`tests/test_rbac.py`** — участник может читать, но не может удалить проект или отправить приглашение (`403`); owner/admin могут; участник A не имеет прав в B.
- **`tests/test_auth_registration.py`** — регистрация создаёт членство **owner** и возвращает рабочий JWT; повторный email отклоняется; запрос без аутентификации — `401`.
- **`tests/test_invitations.py`** — полный поток приглашение → принятие → членство; доступ выдаётся только *после* принятия; принятие с чужой почтой и с истёкшим токеном отклоняется; повторные ожидающие приглашения отклоняются.

## Заметки по деплою

- **Настройки:** задайте `DJANGO_SETTINGS_MODULE=config.settings.prod`. Обязательные переменные: `SECRET_KEY`, `DATABASE_URL` (DSN Postgres), `ALLOWED_HOSTS`. Необязательные: `REDIS_URL`, `SECURE_SSL_REDIRECT`, времена жизни JWT.
- **База данных:** направьте `DATABASE_URL` на Postgres, напр. `postgres://user:pw@host:5432/db`. Без изменений в коде — переключение берёт на себя `dj-database-url`.
- **Статика:** WhiteNoise отдаёт сжатую статику с хешированными именами; `collectstatic` выполняется при сборке Docker-образа.
- **Контейнеры:** `docker compose up --build` поднимает web + Postgres + Redis. Web-образ применяет миграции при старте и обслуживает запросы через Gunicorn.
- **Миграции в проде:** предпочтительнее отдельный шаг релиза (`python manage.py migrate`), а не «удобный» entrypoint.
- **Усиление безопасности (настройки прода):** включены HSTS, защищённые cookie, редирект на SSL и `SECURE_PROXY_SSL_HEADER`; настраивается через переменные окружения.
